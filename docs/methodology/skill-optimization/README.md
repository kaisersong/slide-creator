# Skill 优化方法论

**版本：1.0**

**日期：2026-10-07**

**适用对象：需要改善耗时、token 和产物质量的 Skill 维护者**

这套方法以 slide-creator 的真实优化实验为案例。核心做法是：先记录原始任务的表现，再把重复实现转移到程序中，让模型集中处理内容与判断；通过冻结输入、固定输入对照和完整模型任务，分别验证效率、质量与实际交付。降低上下文长度只是一个手段，最终目标是可靠地完成用户任务。

v1.0 是可复用的方法和模板版本，**不表示 slide-creator 已完成全部质量验收**。案例最新一轮 26/26 自动评测通过，24/24 指定风格正确；人工来源复核仍发现标题改变数量对象、省略并列条件，默认采用暂缓。这个反例也是方法的重要依据：自动评分通过之后，仍需对来源和用户要求作否决性检查。具体实测与边界见 [slide-creator 案例](case-study/slide-creator.md)。

| 文件 | 用途 |
|---|---|
| 本文 | 理解优化思路、执行步骤、验收门槛与常见失败 |
| [优化计划模板](templates/optimization-plan.md) | 在改代码或提示词之前固定目标、基线、语料和验收策略 |
| [评测报告模板](templates/evaluation-report.md) | 汇总前后耗时、token、质量、失败与采用判断 |

| [版本记录](CHANGELOG.md) | 持续记录方法变化及其适用范围 |

优化其他 Skill 时，先复制三个模板到该项目，填完计划，再开始基线。不要把本案例的模型、样本数、阈值或检查器当成所有 Skill 的通用配置。

## 先完成这十个步骤

1. 明确用户任务和最终交付，划清源材料、用户要求、实现规则与外部副作用。
2. 创建隔离 worktree 或等价工作副本，记录原版本、已有失败和运行环境。
3. 固定任务集、重复次数、评分口径、硬失败与采用阈值。
4. 验证计量器和检查器，然后完整运行原始基线，保存原始 usage 与产物。
5. 从真实 trace 和失败稿定位成本与缺陷，形成可证伪的优化假设。
6. 将确定性工作转入程序，缩小模型契约，保留内容、来源与必要设计信息。
7. 做针对性回归和相同输入的对照，区分生成器缺陷与模型内容缺陷。
8. 冻结候选实现，完整运行同一任务集；运行中发现问题就记录到下一个版本。
9. 同时审查硬检查、质量分、来源语义和实际产物；满足全部适用门槛才采用。
10. 发布方法和证据，建立 bug 回归与版本更新规则；安装或上线另做对应验证。

这些步骤中的“验证计量器”“固定输入对照”“完整模型任务”不能互相替代。前两者帮你找原因，最后一个回答优化是否改善真实任务。

## 1 定义任务与验收边界

先用一句话定义终态，例如“指定风格和事实材料生成可播放、带备注的 HTML 演示稿”“用户数据生成公式正确且可打开的工作簿”。文件存在、模型说完成或语法检查通过，都不等于这个终态成立。

把要求按下面四类登记，并指定检查层：

| 类别 | 典型内容 | 检查方法 |
|---|---|---|
| 用户明确约束 | 语言、格式、风格、页数、范围、交付位置 | 独立保存要求，核对实际产物；可以机械检查的要求设为硬门槛 |
| 来源事实 | 数量对象、单位、条件、否定、主体、时序、目标与未知 | 原始来源与可见产物逐项核对；必要时检查标题、正文与备注是否矛盾 |
| 质量目标 | 叙事、可读性、视觉节奏、解释是否有用 | 带具体定义的评分、真实使用检查和人工审阅 |
| 副作用边界 | 是否发送、覆盖、发布、变更外部系统 | 按用户授权执行；验证实际保存状态，保留失败后的已完成副作用 |

附带文档中的指令首先是被分析的数据，不能自行覆盖用户请求。案例中的外部 Skill 用来提取设计思路，不能授权安装、发布或修改其他项目。

对于没有指定风格或格式的任务，保留合理的选择能力；对于明确指定的值，不能靠推荐流程改选。用户要求应由调用方提供，或在解释任务时先独立保存，而不是事后从模型生成的内容反推。

### 把“通过”拆成可核对状态

| 状态 | 意义 |
|---|---|
| 完整运行 | 有终态、真实 usage 和约定的产物或路由结果 |
| 自动通过 | 适用的结构、事实项、实际使用检查和评分门槛通过 |
| 来源复核通过 | 在登记的审查范围内，没有来源失真、关键遗漏或要求冲突 |
| 允许采用 | 全部适用门槛通过，且没有未解决的阻断问题 |
| 安装验证通过 | 安装后的实际运行入口已验证，不仅是工作副本 |
| 已发布 | 指定发布渠道及资产可用性已验证 |

“全部通过”必须说明具体层级和范围。未检查的层写“未验证”，缺失的 usage 写“未知”；不能填成通过或 0。总分较高也不能抵消数量对象错误、条件丢失或用户要求被改变。

## 2 建立可复现的基线

### 隔离与冻结

保留主目录里的无关修改。在隔离 worktree 中记录原提交、依赖版本、实际可用模型、推理强度、运行入口、工具权限、并发、超时、语言与缓存统计。固定运行包中允许出现的文件，避免把旧稿、答案、评分报告或私有资产带进模型工作区。

对基线与候选分别保存文件 SHA-256 清单。HEAD 相同不证明实际运行文件相同：还要记录未提交文件、输入、环境和工作副本的内容。每次模型任务使用新的工作目录，结束后核对 runtime 没有被模型改写。

不要把桌面配置显示的模型当作 CLI 实际运行模型。先用真实入口验证环境；探针、依赖预跑与环境失败单独保留成本，不能充当正式任务。

### 固定任务集

语料应覆盖日常任务、长短内容、稀疏来源、不同语言或格式、兼容旧输入、异常输入与负向路由。负向路由指明确不应该生成该类产物的请求，例如只要聊天中的文字，或只要导出既有文件的说明。

对有随机性的任务做多次重复。slide-creator 使用 8 个正向任务各 3 次，另加 2 个负向任务各 1 次，形成 26 次正式臂；这是案例规模，不是普遍充分的样本量。另保留未用于逐轮调优的任务作为留出集，避免对固定语料过度优化。不断修改语料时，要发布新的语料版本并安排可比的基线。

### 已有失败不能长期变成免责项

记录原版本失败的具体输入、行为与来源契约。区分产品缺陷、过时测试和检查器错误：

- 真实产品缺陷应修复，再证明新旧差异。
- 过时断言应说明其为何违背当前契约，用明确来源输入替代；不能直接删掉测试以获得全绿。
- 检查器错误应独立修复并校准受影响臂，不能把分数变化记为产品优化。

案例最初有两项 Fantasy Rainbow 基线失败。后续既补回缺失字段与代码/快捷键语义，也移除要求生成器编造宣传语的旧断言，改用明确输入验证。最后的回归检查不再有这两项失败。

## 3 先验证计量器和检查器

在花费完整模型评测预算前，给检查器准备已知正确、已知错误的产物。验证它能抓到错风格、漏事实、错误数字绑定、裁切、同文重复、缺失备注和错误路由，也不会误判正常的标识符或合法未知值。

视觉或交互检查必须操作真实使用路径。进入播放模式、切页、等待字体和动画稳定后，再核对实际活动页、可见内容与视口位置。不要只设置一个 CSS 类然后假定页面已经进入目标状态。文档、工作簿或系统操作应选各自对应的真实入口。

当检查器出错时，保留原判定和原生成收据，在新的评估目录中重查受影响产物。对可比的基线与候选使用相同校准口径；如果新协议改变了模型输入或工具面，旧生成不能自动代表新协议，需安排新的基线。额外 QA、截图与评审成本单独登记。

### 统一计量口径

| 指标 | 定义与边界 |
|---|---|
| 生成耗时 | 从实际模型 CLI 启动到终态；包含读资料、推理、工具调用、修复与程序生成 |
| input tokens | provider 的真实累计输入；包含缓存输入时明确说明 |
| cached input tokens | 缓存输入单列，缺失为未知 |
| uncached input tokens | input 减 cached，两个值齐全时才能计算 |
| output tokens | provider 报告的输出；已含 reasoning 时不能再重复相加 |
| total tokens | 本次 provider 口径下的 input 加 output，不能用最终文件字节数估算替代 |
| 评测全链路 | 生成加程序 QA、真实使用检查及独立审阅；审阅 token 单列后再汇总 |
| 校准与研究开销 | 环境探针、作废检查器评审、协调者研究等单独登记，不冒充每份产物成本 |

usage 有时是累计收据，有时是逐调用增量。先读该运行入口的真实事件语义，决定去重或求和。案例的 CLI 同一轮重复输出累计 usage 时使用最后一个有效收据，没有把重复收据相加。其他入口不能直接照抄这个解析规则。

报告每次结果、总消耗、均值、中位数和 p90，并说明 p90 算法。主要比较应做相同任务的配对，另看每类任务均值；重复来自同一主题时，不能当成独立主题扩大统计置信度。案例使用按任务簇 bootstrap 的区间，但 8 个固定主题不能支持广泛性能结论。

缓存、服务负载、网络和运行时段会影响耗时与账单。总 token 减少不等于付费同比例下降，顺序运行的两臂也不能证明全部耗时变化来自代码。

## 4 从真实失败提出优化假设

先看 trace 中模型读了什么、生成了什么、修了几次，再看最终产物缺了什么。把可证伪的假设写入计划：

| 假设 | 要改变的因素 | 验证证据 | 如何被否定 |
|---|---|---|---|
| 重复读取实现增加上下文 | 给模型精简契约，程序加载完整实现 | 真实读文件 trace、usage、完整模型任务 | token 没降或内容质量明显回退 |
| 卡片容量造成事实丢失 | 修布局预算和内容承载 | 同一输入的旧/新实际产物 | 输入本身没有该事实，或修后仍不可见 |
| 数字被绑定到错误标签 | 显式保留事实对象、值与单位 | 按卡片检查源实体，再核对整页 | 只有数字出现，对象仍错误 |
| 模型改变了指定风格 | 从请求独立保存选择，写入前核对 | 错误输入故障注入、完整任务结果 | 删除参数或传冲突值仍可写出错误风格 |

每个版本尽量围绕少数相关假设。先做故障复现、局部回归、固定输入实验，再用独立标记的小规模模型探索筛掉明显失败方案，最后才投入完整验收臂。探索任务也保存成本与结果，但不能补进正式臂凑成全通过。把同一根因的相关修复在冻结前完成，减少每个微小改动都重跑全量的成本。不得在同一正式臂中边跑边改实现；发现 bug 后保持该臂不变，另建候选。固定输入对照、读文件消融或契约对照只能支持所控制变量的影响，不足以把整轮收益归因于某一条提示词。

## 5 将模型与程序的责任分开

模型适合提取内容、组织论点、解释证据、选择需要判断的设计。程序适合模板展开、样式注入、布局计算、文件打包、固定交互、确定性校验和约束执行。

slide-creator 采用 BRIEF 作为中间表示：模型写结构化内容，canonical renderer 读取完整风格与 runtime，生成最终 HTML。模型不必每次重新实现 CSS、JavaScript、播放控制和导出 DOM。其他 Skill 可以使用文档大纲、表格计划或操作清单作为自己的中间表示，但应保留领域所需语义。

### 中间表示应能承载真实内容

字段应明确区分来源事实、推论、目标、建议、行动与演讲/操作说明。涉及量化和决策时，至少应能保留对象、值、单位、条件、主体、时间和来源定位；稀疏材料允许未知或更少内容，不能靠重复、序号或虚构数字填满组件。

兼容旧输入时，新字段先考虑可选与明确 fallback，验证旧文件、缺失字段、部分配置和未知值。不能为优化一个新案例，静默改变原有格式或丢掉已有内容。

程序展开不等于程序理解来源。一个形式正确的中间表示仍可能写错事实，最终标题也可能违背正确正文。因此需要分别验证输入语义、生成器内容承载和最终可见产物。

### 渐进式披露应保留完整能力

入口文档只保留路由、核心规则、输入输出、失败处理和所需资源。模型按任务读取精简契约，程序仍加载完整实现。契约应从现有 schema、能力注册表和样式 owner 生成，避免维护另一份会漂移的手写能力清单。

设计决策超出契约时，再读相关参考；实现错误由维护者修复。禁止每份任务都让模型读源码、改生成器来绕过模板缺陷。不要为了降低 token 任意规定“最多读三个文件”，也不要通过删除必要证据缩短契约。

外部 Skill 的有用模式需要映射到本项目：哪个工作交给模型，哪个交给程序，如何验证其有效。源码被程序展开成更大页面只是机制证据，不是 token 节省比例；实际比例只能来自任务运行。

### 用户要求应成为程序约束

案例中的指定风格最初只存在自然语言和模型生成的 BRIEF 中。模型把 Strategy Consulting 写成 Swiss Modern，程序仍照 BRIEF 生成。后续由调用方先保存独立请求，再由生成器核对，不一致就拒绝写出，要求纠正 BRIEF 后重试；支持别名和自定义主题，保护已有产物。

对其他 Skill，可将语言、格式、目标位置或操作范围按同样方法提供给执行层。输入约束必须来自正确解释的用户请求，不能从输出反推；检查程序约束成立不等于证明自然语言抽取永远正确。约束文件的解析、作用目录、显式路径和冲突规则都要写清并测试。

## 6 设置互补的验证层

| 验证层 | 核对什么 | 单独不能证明什么 |
|---|---|---|
| 结构与协议 | schema、格式、字段、来源标记、输出路由 | 事实正确、实际可用或用户要求完成 |
| 组件回归 | 原失败输入、边界、旧格式兼容、拒绝覆盖 | 随机模型任务的质量与成本 |
| 固定输入对照 | 相同中间表示下的旧/新程序行为 | 模型会写出正确中间表示 |
| 完整模型任务 | 从用户要求与来源到最终产物、终态和 usage | 所有未知任务或其他运行入口都适用 |
| 真实使用 | 实际打开、交互、导出、保存状态及可读性 | 全文语义均忠于来源 |
| 独立来源审阅 | 标题、正文、备注、条件、实体、来源强度 | 判分永远准确、所有输入都通过 |
| 安装与发布 | 安装入口、分发资产和目标系统状态 | 未测试的外部渠道或消费环境可靠 |

硬失败应独立于平均分：关键事实遗漏、数量对象或单位错误、并列条件被删、用户要求冲突、虚构已验证结论、产物不可用、错误外部副作用。先核对输入事实，再核对最终可见内容；页码、装饰、隐藏 DOM 或备注中出现数字，不能替代正文。

独立评审器只看到匿名产物、来源与要求，不看到候选标签、优化目标或“这个版本更好”的提示。记录评分定义、问题证据、实际截图/输出与评审成本。模型评分可以辅助覆盖，人工来源审查保留否决权；否则低成本错误可能被较高均分掩盖。

### 标题必须单独检查来源忠实度

标题更短、更醒目，因此更容易把条件和对象压掉。以下几种改写都需要纠正：

| 来源 | 失真改写 | 原因 |
|---|---|---|
| 两位受监管客户仍需数据驻留审查 | 两项审查尚未完成 | 客户数变成了审查数 |
| 成本增加且满意度未改善时停止扩展 | 成本恶化即停 | AND 条件变成单一条件 |
| 访谈提示沟通不透明 | 沟通是已确认根因 | 线索变成因果证明 |
| 可用性目标为 99.9% | 可用性已达到 99.9% | 目标变成结果 |

无法把完整条件放入短标题时，用不改变逻辑的中性标题，把完整决策规则放在同一可见区域；然后审查两者有没有矛盾。这个处理方向仍需在相应 Skill 中实现并验证，不能因为正文正确就豁免标题。

### 视觉检查要定义测量对象

测量字号时明确选择哪些节点、长度阈值、隐藏与装饰排除规则，以及播放缩放。重复计数要说明是完全同文、完整句还是语义复述，是页内还是跨页，是否保留必须相邻的指标标签与来源。

同一节点在两个视口、两种模式会被观察四次。观察数不能写成不同错误数量。诊断漏掉某类组件后，应升级诊断版本并重新量测可比产物，保留旧记录。

布局多样性只是诊断，不能代替美学与叙事质量。用真实内容验证长文本、稀疏事实、最小与最大页数，不得为了消除溢出静默删内容，或为了视觉饱满重复填项。

## 7 完整运行与采用判断

开始前冻结输入、候选、评分器版本和阈值。固定并发与超时，每次结果保存用户请求、来源、prompt、trace、stderr、usage、中间表示、最终产物、检查结果、截图和评审。已结束的结果不可覆写；中止目录先核对副作用，不能盲目重放。

完整报告应给出失败、慢样本、缺失 usage、中止成本及校准成本。模型未完整运行与“运行完成但产物失败”是不同结果，两个分母都要展示。程序检查不通过的任务不能从耗时和消耗统计中消失；不完整结果不能冒充有效质量分。

### 阈值是计划的一部分

案例首次效率优化以生成 token 中位数至少减少 10% 为目标，同时限制耗时与质量回退。已有高效通过版之后，维护精修允许 token 和耗时中位数最多增加 10%，质量配对均值回退不超过 3 分、每类任务均值回退不超过 5 分，并禁止新增硬失败或逐次 pass 回退。技术语言按用户要求降为观察项，政策变更有记录，质量门槛保持不变。

这些数值仅是本案例政策。其他 Skill 应按用户任务、风险和预算事先决定门槛；首次提效和后续质量维护可以使用不同目标，但不能看到失败后临时放宽标准。

采用必须同时满足效率政策、所有适用硬门槛、来源复核与任务质量。整体均值改善不能掩盖单类任务退化；自动通过与人工复核冲突时，登记反例、暂缓受影响的采用结论，再修复和复测。修好某一个问题，可以单独确认该问题已解决，无需把它扩大为整个 Skill 已验证。

反复在固定任务上调优后，应运行留出集和代表性新任务。模型、运行入口、并发、工具、语料或检查协议变化时，评估是否需要重跑基线；复用旧基线必须说明服务时段、缓存和其他可比性限制。

## 8 这次实验踩过的坑

| 问题 | 根因与处理 | 可迁移检查点 |
|---|---|---|
| token 明显下降但初期质量回退 | 精简读取后，模型无法再通过读实现补偿模板缺陷；先修内容承载 | 不以 token 成功替代完整质量验收 |
| 人工切换 DOM 类造成假空白 | 检查器没有通过真实 controller 激活页面；校准两臂 | 对已知正确交互做检查器自测 |
| p95、版本号被当作测量值 | 数字识别缺少上下文；识别指标值与标识符 | 不只搜索裸数字 |
| 24 小时配给 TLS，7 天配给 token | 从全局数字串和无关句子配对；绑定卡片自己的源事实 | 检查对象、值、单位与作用范围一起正确 |
| 固定卡片数导致截断、重复或补事实 | 模板容量与真实事实量不匹配；允许稀疏与完整声明 | 检查最后一条事实、最长声明和空列 |
| 无真实前后关系却使用 Before/After | 布局替来源引入了评价；改用证据或流程 | 展示语义也属于事实审查 |
| 不同单位组成同一数值系列 | `%`、毫秒和百分点不可直接比；改卡片或分组 | 图表单位、基线、时间范围必须一致 |
| 字号和重复诊断提前宣布清零 | 漏掉 Insight div、pre/code 等节点；升级 v4 再测旧新产物 | 测量覆盖有版本，明确统计分母 |
| 排重删掉数量标签或不同条件 | 文本相同不代表语义可删除；保护绑定，保留否定与新句 | 回归十进制、条件、否定及标签关联 |
| 模型选错指定风格 | 仅信任模型写的 BRIEF；改为独立请求加写入前核对 | 明确要求不交给推荐流程决定 |
| 26/26 自动通过仍有严重来源问题 | 评分均值不足以发现实体和条件失真；人工否决并保留反例 | 标题与关键决策设专项审查 |
| 为完成新回归而改旧测试 | 可能隐藏产品问题；先对照契约与来源再改断言 | 原失败、修改理由和新输入必须可追踪 |
| 登录 shell 换掉 Python 环境 | PATH 预期与真实入口不同；使用正确绝对路径或显式 PATH | 环境探针与正式任务使用同一入口 |
| 全量评测轮数过多 | 本案例累计312次正式生成/路由任务；优先低成本定位、相关修复成组，正式臂前筛除已知失败 | 单份提效与研究总成本分别计量，设置预算与中止条件 |
| 中途修代码再继续同一臂 | 混合版本无法比较；冻结旧臂，新候选新目录 | 每个产物与实际 runtime SHA 对应 |

源实体专项检查也有盲区：仅检查数字卡，可能漏掉标题或说明中的错误；完全同文计数不会发现语义复述；检查必需数字出现不会发现“数字正确、归属错误”。每项检查都要写覆盖范围，不能把多个窄检查相加当作全文证明。

## 9 把方法迁移到其他 Skill

| Skill 类型 | 可转入程序的工作 | 应保留给模型的判断 | 重点验收 |
|---|---|---|---|
| 报告或文档 | 模板、样式、目录、引用格式、输出与结构校验 | 事实组织、论证、受众适配 | 标题与来源一致，引用支持对应主张，最终文档可读 |
| 表格或分析 | 公式、数据转换、格式、复算与文件检查 | 指标选择、假设与业务解释 | 来源粒度、单位、公式结果、图表和保存状态 |
| 图表或演示 | 组件、布局、运行交互、打包与导出 | 展示语义、叙事与证据关系 | 数值绑定、完整条件、可读性、交互及导出 |
| 系统操作 | 参数校验、范围约束、去重、幂等与结果读取 | 解释用户意图、选择适用操作 | 原始授权、真实副作用、部分完成与重试安全 |

这些是迁移起点，不是以上 Skill 的实测优化结果。先用该项目的真实任务建立基线，再选择要转移的职责，不要把 slide-creator 的正文 22px、BRIEF schema 或 HTML 检查照搬过去。

预算有限时，可以减少不相关调研、提前用故障注入校准检查器，并在正式臂前完成固定输入实验；缩减正式任务范围时必须同步缩小结论。先明确预算和中止规则，记录已完成的调用与副作用。不能让“低 token”建立在少做任务或隐藏失败上。

## 10 新 bug 与版本更新

发现 slide-creator 或其他采用本方法的 Skill 的 bug 时，复制 [bug 模板](templates/bug-record.md)，记录最小输入、真实产物、源要求、复现环境、严重性与影响范围。优先判断问题位于请求解析、契约、中间表示、执行/渲染、检查器、评审还是交付层。

修复后至少完成原失败复现、针对性回归和受影响真实入口验证。涉及模型契约、生成路径或用户可见语义时，重新冻结候选并完整评测约定任务集；涉及计量器/检查器时，还要重新校准受影响历史比较。只改文字说明或局部无关文档，不必重跑完整模型评测。

将真实失败加入固定回归输入。留出集用于泛化检验；如果一个留出任务已被反复用于调参，应明确将它转为调优集，并补充新的留出任务。不要让有害输入既成为调优样本，又被继续称为未见测试。

### 方法论版本规则

| 更新版本 | 适用变化 | 必须留下的记录 |
|---|---|---|
| 1.0.1 等补丁 | 澄清措辞、补充已有原则下的案例或修正文档错误 | bug ID、纠正点、原结论是否受影响 |
| 1.1 等次版本 | 新增检查层、模板字段、失败分类或方法步骤 | 为什么现有方法漏检、旧项目需补哪些验证 |
| 2.0 等主版本 | 更改计量定义、通过语义或采用门槛，导致旧结论不可直接比较 | 迁移说明、重新计量范围和新旧口径并列表 |

Skill 实现版本、方法论版本、语料版本、评分器版本和验收政策版本分别管理。发现 Skill bug 不必每次重写整个方法，但必须判断是否暴露方法盲点；若影响旧结论，要标注旧结论受影响，并追加纠正记录。方法论正式更新时在 [CHANGELOG](CHANGELOG.md) 记载版本、日期、bug、规则变化、补验收要求与证据。

已完成的历史快照、模型收据和评审不覆写。新的方法版本发布前核对内部链接、统计、模板字段与案例状态；保留旧方法版本的 Git 提交或发布包。未来更新由实际 bug 和修复验证触发，本 v1.0 没有创建自动监控任务，也没有承诺未经验证就更新结论。
